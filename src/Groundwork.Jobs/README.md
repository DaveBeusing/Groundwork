# WP01-L3B Jobs

Compose one `JobScheduler` per Core world. Give it that world's execution authority, input source, ownership scope, fault reporter, runtime clock and a fixed handler registry. The host retains the phase, writer and publication capabilities. The scheduler implements `IJobScheduler`.

- Submit with the currently open gameplay or base phase. Unknown handlers and invalid Core descriptors fail admission. Local queue and worker caps are enforced independently of Core's descriptor, output and retention reservations. Admission also checks ownership headroom. An invocation without input needs its record plus one credit shared in succession by dispatch and worker custody. For capture jobs, the scheduler holds custody before asking Core to check pin capacity. If that check is temporarily blocked, the job stays pending. If capture still runs out of capacity after authorization, the scheduler cancels the permit without invoking the handler and exposes the reason on the execution report.
- During the phase, call `DispatchReadyAsync` to scan pending work in canonical source order. It captures input for jobs Core authorizes and schedules their handlers off the coordinator thread. The call does not wait for handlers. The host may scan again while the phase is open. Jobs still waiting when it closes remain pending for their next eligible phase.
- The handler receives read-only copied arguments, a read-only input façade and its own bounded output writer. The writer closes on cancellation or local stop. Input remains usable by cancellation callbacks until they finish, then is released before Core execution settles. An owned snapshot can outlive its capture phase. An append or output failure invalidates the invocation result even if the handler ignores it. Core and the ECS writer retain authority for commit, conflict handling and target-version checks.
- Keep the admission handle until observation and receipt copying are complete. Casting it to `IJobExecutionHandle` exposes an execution-completion task with the original exception and distinct cleanup failures. A cleanup-only fault uses one atomic Core observation with code 2, with its exception preserved in the operational cleanup list. Execution completion does not imply command commit. A terminal dependency failure becomes visible in Core immediately and completes the task when the scheduler next scans or drains the pending entry.
- The host first latches Core runtime shutdown, then awaits `StopAsync` with that runtime deadline. The scheduler stops admission, cancels queued work and signals active invocations. Handler code and token callbacks run independently of the coordinator. An expired wait raises `IncompleteCleanupException`. Unacknowledged workers and uncertain input cleanup retain their Core ownership leases for custody.

## Verification and measurements

```powershell
dotnet restore tests/Groundwork.Jobs.Tests/Groundwork.Jobs.Tests.csproj --locked-mode
dotnet test tests/Groundwork.Jobs.Tests/Groundwork.Jobs.Tests.csproj -c Release --no-restore --logger "console;verbosity=detailed"
```

`ReadMetrics` exposes admitted and rejected counts, backlog, occupied worker slots, completion counts and accumulated clock ticks. Queue wait covers accepted submission through capture and dispatch. Worker busy time covers invocation through settlement. Cancellation time covers observed cancellation through settlement. Dispatch time measures synchronous coordinator scans, including the input provider, and excludes worker waits. The tests print a 32-job no-op sample and a cooperative cancellation sample. The utilization sample divides busy time by elapsed wall time with one configured worker. These samples describe the test fixture and scheduling overhead. They do not set performance thresholds.
